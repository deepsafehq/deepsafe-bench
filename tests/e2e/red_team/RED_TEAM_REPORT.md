# DeepSafe Provenance Services: Red Team Report

**Date:** 2026-03-29
**Scope:** 4 provenance detection services (c2pa-checker, sdxl-watermark-detector, audioseal-detector, videoseal-detector)
**Objective:** Find false positives, false negatives, crashes, and information leakage

---

## Executive Summary

**Overall Assessment: STRONG with one critical weakness.**

The provenance detection system is well-hardened against most attack vectors. The C2PA trust chain, AudioSeal, and VideoSeal are all robust against false positives and malformed input. However, the SDXL invisible watermark detector has a **fundamental, unfixable vulnerability**: the symmetric watermarking scheme allows anyone to forge watermarks into real photos, causing false positives.

| Category | Result |
|----------|--------|
| C2PA + EXIF trust chain bypass | **BLOCKED** |
| SDXL watermark forging (false positive) | **6 CRITICAL vulnerabilities** |
| AudioSeal false positives | 0/21 patterns triggered (PASS) |
| VideoSeal false positives | 0/19 patterns triggered (PASS) |
| Service crashes / OOM | 0 crashes across 26 tests (PASS) |
| Information leakage | LOW (docs/model names exposed) |
| Timing oracles | LOW (SDXL 2x slower for watermarked images) |

## Vulnerabilities Found

### CRITICAL: SDXL Watermark Forging (False Positive)

**Severity:** Critical
**Service:** sdxl-watermark-detector (port 9002)
**Impact:** An attacker can make any real photograph appear AI-generated by embedding a forged SDV2 watermark.

**Root Cause:** The invisible-watermark library uses a symmetric encoding scheme. The encoder is publicly available (MIT license, `pip install invisible-watermark`). Anyone can encode the exact SDV2 prefix (`b"SDV2" + b"\x00" * 13`) that the detector looks for.

**Attack Steps:**
```python
from imwatermark import WatermarkEncoder
from PIL import Image
import numpy as np

# Load any real photograph
real_photo = np.array(Image.open("real_photo.jpg").convert("RGB"))

# Forge the SDXL watermark
encoder = WatermarkEncoder()
encoder.set_watermark("bytes", b"SDV2" + b"\x00" * 13)
forged = encoder.encode(real_photo, "dwtDct")

# Save as PNG (lossless preserves watermark)
Image.fromarray(forged).save("forged.png")
# This image now returns probability 0.85-0.92 from the detector
```

**Results:**

| Attack | Format | Probability | Status |
|--------|--------|-------------|--------|
| Forged SDV2 512x512 | PNG | 0.85 | FALSE POSITIVE |
| Forged SDV2 1024x1024 | PNG | 0.92 | FALSE POSITIVE |
| Forged SDV2 via dwtDctSvd | PNG | 0.92 | FALSE POSITIVE |
| SDV1 prefix (1 char diff) | PNG | 0.85 | FALSE POSITIVE (fuzzy match) |
| SDW2 prefix (1 bit diff) | PNG | 0.85 | FALSE POSITIVE (fuzzy match) |
| Forged SDV2 any size | JPEG | 0.50 | JPEG compression destroys watermark |
| Forged SDV2 256x256 | PNG | 0.50 | Too small for reliable encoding |

**Mitigating Factors:**
- JPEG compression destroys the forged watermark (most web images are JPEG)
- Images < 512px are too small for the watermark to survive
- This is a known limitation of all symmetric watermarking schemes
- In the ensemble, SDXL watermark is one signal among many

**Recommendation:** This is fundamentally unfixable in the symmetric watermarking model. Options:
1. Document as a known limitation
2. Downweight SDXL watermark signals in the ensemble (it should never be the sole basis for a "fake" verdict)
3. Add a disclaimer that watermark-only detection is not tamper-proof
4. Consider removing the SDXL detector entirely if the false positive risk outweighs the detection value

### LOW: Information Disclosure via API Endpoints

**Severity:** Low
**Services:** All four
**Impact:** Internal model names, device info, and full API schemas are exposed.

All services expose:
- `GET /` — Returns model name, description, device type, model_loaded status
- `GET /health` — Returns model name, device type, model_loaded status
- `GET /docs` — Full Swagger UI
- `GET /redoc` — ReDoc documentation
- `GET /openapi.json` — Full OpenAPI schema with parameter names and types

**Leaked Information:**
```json
{
  "model_name": "audioseal_detector",
  "device": "cpu",
  "model_loaded": true,
  "description": "AudioSeal watermark detector for AI-generated audio"
}
```

**Risk:** If these services are ever exposed externally (directly or through a misconfigured proxy), an attacker gains:
- Knowledge of exact model names and detection approaches
- Whether a model is loaded (useful for timing attacks)
- Full API schema for crafting attacks

**Recommendation:**
1. Disable `/docs`, `/redoc`, `/openapi.json` in production
2. Remove model names and device info from root/health endpoints
3. Return only `{"status": "healthy"}` from health checks

### LOW: SDXL Timing Side Channel

**Severity:** Low
**Service:** sdxl-watermark-detector
**Impact:** An attacker can infer whether an image contains a watermark by measuring response time.

**Findings:**
- Non-watermarked images: avg 15.9ms
- Watermarked images: avg 32.6ms
- Ratio: 2.05x

The detector tries `dwtDct` first, then `dwtDctSvd`. When the first method finds a match, it returns early. When both methods fail, both run in full. This creates a measurable timing difference.

**Risk:** Low. This only tells the attacker whether a watermark exists — information that's already returned in the API response. It would only matter if the API were modified to hide the detection result.

## Confirmed Defenses (Attacks Blocked)

### C2PA + EXIF Trust Chain: SECURE

The hardening of EXIF/IPTC tag trust is working correctly:

1. **EXIF injection without C2PA** returns `None` (ignored) — PASS
2. **Combined EXIF+IPTC injection without C2PA** returns 0.5 — PASS
3. **C2PA-signed image + EXIF injection**: exiftool modifies the file bytes, which invalidates the C2PA signature. The service correctly sees `validation_status` has issues, sets `sig_valid=False`, and the EXIF tags are then untrusted. — PASS

The C2PA library also rejects self-signed certificates at signing time, preventing trivial manifest forging.

### AudioSeal: ZERO False Positives

Tested 21 distinct audio patterns:
- Silence, white noise, pink noise
- Sine waves at 20Hz, 440Hz, 15kHz
- Speech-like multi-tone audio
- Near-clipping and near-zero amplitude
- Impulse trains, square waves, chirps, AM modulation, DC offset
- 8kHz, 22.05kHz, 44.1kHz, 48kHz sample rates
- Stereo audio
- 100ms and 10s durations

**All returned exactly 0.5.** The AudioSeal model's 0.3 confidence threshold is effective at filtering noise.

### VideoSeal: ZERO False Positives

Tested 19 distinct image/video patterns:
- Solid colors (white, black, gray)
- Random noise, low-contrast noise
- Gradients (horizontal, vertical)
- Checkerboard patterns
- High-frequency sinusoidal patterns, moire, diagonal stripes
- Extreme dimensions (1x1, 16x16, 64x64, 1024x1024, 2048x2048)
- Control video file

**All returned exactly 0.5.** The 0.6 bit confidence ratio threshold is well-calibrated.

### Input Handling: ROBUST

All services correctly handle:
- Empty payloads (400 error)
- Invalid base64 (400 error)
- Random garbage bytes (returns 0.5)
- Single null byte (returns 0.5)
- Truncated JPEG/WAV headers (returns 0.5)
- 8192x8192 images (processes slowly but doesn't crash)
- Missing/wrong field names (400/422 errors)
- 20 concurrent requests (0 errors)
- 10 concurrent requests to model-loading service (0 errors)
- Non-image data sent as image (returns 0.5, no error leakage)

No stack traces, internal paths, or model details are leaked in error responses.

## Known Limitations (Not Bugs)

### 1. Symmetric Watermark Forging (SDXL)
As documented above — fundamental to the approach. The invisible-watermark library's encoder is public.

### 2. Metadata Stripping Evasion
Any AI-generated content that has had its metadata stripped (screenshot, re-save, social media upload) will return 0.5 from the C2PA checker. This is expected — provenance detection only works when provenance data is preserved. The ensemble's artifact-detection models handle this case.

### 3. AudioSeal/VideoSeal Forging (Theoretical)
The AudioSeal encoder (MIT license) and VideoSeal encoder (MIT license) are publicly available. An attacker could watermark real human speech/video to cause false positives. This was not tested in this engagement due to environment constraints, but the same symmetric-key limitation applies as with SDXL.

### 4. Large Image Processing Time
8192x8192 images take ~29s on the SDXL detector. While not a crash, this could be exploited for slow-loris style resource consumption.

## Recommendations

### Must Fix
1. **SDXL watermark weight in ensemble**: Ensure the SDXL watermark signal alone can never push the final verdict above the fake threshold. It should be corroborative evidence only, not sufficient on its own.

### Should Fix
2. **Disable API documentation endpoints** (`/docs`, `/redoc`, `/openapi.json`) in production builds
3. **Minimize health/root endpoint data** — return only `{"status": "healthy"}` without model names or device info

### Nice to Have
4. **Add image size limits** — reject images larger than 4096x4096 to prevent slow processing
5. **Add request timeout** at the service level (not just client-side) to cap processing time
6. **Consider constant-time response** for SDXL detector to eliminate timing oracle (add artificial delay to fast responses)
